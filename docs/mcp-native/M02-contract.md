# M02 — minimum MCP worker contract and threat model

Frozen before implementation, 22 November 2026 AEDT. Parent `a59d76c6272d4848642d90906929d63d4cb318ac`; M01 discovery complete, not live qualification. This is an offline design, not an installation or live-test grant.

## Architecture and authority

Keep the existing succession.core.Controller as the sole decision and dispatch authority. Inspect its exact source and integration/runner.py and repo_reader.py at this parent. The core expects a completed assistant Response and a RepoView, deduplicates (chat_id, response_id), reserves one Pending action and applies cap/terminal logic. The adapter must never simply treat an MCP event as a complete assistant Response. It can project a qualified report onto the core's status vocabulary only after independent gates below, preserving actual provenance as an MCP report rather than asserting native message identity. No alternate controller. Existing GitHandoffReader validates fresh remote tip and the three trailers; require additional independent equality to the report's claimed SHA and authorized exact branch (no implicit branch expansion). Use a test-only adapter with injected observations; production MCP and launcher later.

## Contract v1

Controller-owned private reservation: immutable run_id, action_id, kind (bootstrap/CONTINUE_CURRENT/LAUNCH_SUCCESSOR), worker ordinal, exact account_key, stable project_id, repo, authorized branch, expected source saved chat (null only for bootstrap), expected source report anchor, prompt digest, challenge digest, expiry, config cap. Fresh cryptographically random one-use challenge per dispatch, including same-chat continuation; store only digest, never Git or tool outputs/logs. Challenge is correlation evidence carried in the posted assignment, **not** account authentication or secret proof of original message. Reserve once, persist before any possible submission; when attempt uncertain keep reservation and no retry. If a challenge expires after possible Send, hold and reconcile; do not silently replace it.

Two bounded, explicit mutating tool operations, no shell, Git write, navigation, arbitrary URL or arbitrary task forwarding:
- register_worker: schema_version=1, run_id, action_id, challenge. Server independently gets validated authenticated principal and client session/subject metadata, not body claims. Record one provisional registration for the active attempted reservation; same exact retry returns original receipt; another principal/session/subject or conflicting attempt is rejected. Registration is not delivery or worker count. Receive only minimal receipt/worker ordinal or pending binding indication; no private route/session token. Existing worker may poll via idempotent retry for bound status.
- report_worker: schema_version=1, run_id, action_id, status in NEED_MORE_TIME/TASK_COMPLETE/ERROR, publication_sha (required only for TASK_COMPLETE, null otherwise), publication_branch (required only for TASK_COMPLETE, null otherwise). At most one immutable report per action, derived server event ID from reservation identity (not model-supplied native message ID). Return received/duplicate/hold, not completion or launch claim. Must match the bound registration principal/session/subject, current action and verified delivery. No call body account/Project/saved-chat claims trusted. Exact duplicate idempotent; conflicting report holds without a second action. ERROR is a hold, never implicit owner approval. NEED_MORE_TIME is same-chat only. No unbounded model-controlled continuation; explicit run policy and existing cap, deadline and pause apply. Missing call holds/waits, not automatic retry.

For M03 use strict schemas (reject unknown/missing fields, unexpected types, invalid statuses and malformed SHA/ref; never coerce). Synthetic trusted context is injected separately from the JSON body; mock authentication is explicitly not a live auth result. Require nonempty session and subject and a validated principal scoped to the exact run/account; absent/mismatch fails closed. In M04 independently test real auth availability, metadata forwarding, stability across retries/restarts and absence behavior. A per-launch nonce alone, OAuth alone, subject alone, or session alone is insufficient. Reuse no credential/tunnel/service. Mark the tools as mutating; accurately annotate their possible indirect effects before live connection.

## Evidence predicates and order

1. Controller reserves/persists before Send, verifies exact account/Project, known genuine empty composer/no attachments, allowed source/target, pause and cap. For bootstrap verify offline bounds and distinct new chat; for continuation require same saved chat; successor distinct from all admitted IDs. Read exact posted prompt/digest and independently observed saved ID/route after Send. Receipt is not a callback, and a callback is not a receipt.
2. Correlate receipt of exact unique challenge-bearing posted assignment to provisional registration for that single reservation. Bind authenticated principal and session/subject to independently observed saved chat. For continuation require prior binding of all those identities; successor must have a distinct saved ID and distinct session, same authorized principal/subject. If route, session-to-saved-chat mapping or receipt ambiguous, HOLD. Never trust body/chat self-report to establish binding. The matching challenge establishes practical correlation under bounded exclusive launch and authenticated user scope, not cryptographic proof of host conversation identity; M05 must independently establish actual target and exclude competing delivery before live acceptance. Stable session mismatch is a hold, not a new worker.
3. Only controller adopts delivery and invokes core confirm; no count change on provisional registration. Report before verified delivery not actionable (reject and await exact authorized retry). A valid accepted report is a durable immutable observation; duplicate callbacks cannot dispatch or advance. Reject stale run/action, wrong session, wrong principal, unauthorized branch or invalid schema; conflicts from the bound caller hold for reconciliation.
4. For TASK_COMPLETE independently retrieve authorized remote tip with GitHandoffReader equivalent; compare exact claimed SHA, run, saved worker trailer, repo, branch, next task/terminal semantics, and freshness against prior accepted publication. Mock remote reader explicitly separate from MCP args. Hold without consuming the report on absent/unpublished/stale/different tip, mismatched run/worker/ref or inconsistent terminal/next-task. If tip changes before adoption, hold/recheck. No git commands from arbitrary request values.
5. Separate independently observed quiescence anchored to the same saved chat and reserved turn (completed assistant response or otherwise positively established equivalent idle/turn evidence), and check it remains valid immediately before any later UI effect. A callback timing, absence of tool calls, elapsed time, Git publication, or a model assertion is not quiescence. Wait or bounded hold if unavailable. M03 mocks true/false/unknown; M05 qualifies actual readback. No invented native message ID.
6. After gates pass, use a durable action-scoped report anchor and three core statuses. Map only verified report to core Response with complete=True and correct saved identity; provenance remains tool report, not an attested native message. Feed verified RepoView only when required. Existing core chooses STOP_FINISHED, STOP_CAP, HOLD, CONTINUE_CURRENT or LAUNCH_SUCCESSOR. Persist consumption and prepared action with adapter evidence atomically, before any dispatch. Controller alone may send, with same pre-Send and readback rules. No implicit retry after possible submission; fail closed on missing/corrupt ledger.

Durable POC state: one serialized writer, private run config/route, core state, current reservation (phase prepared/sending/uncertain/bound), registration binding, immutable report and consumed action history, prior accepted SHA, pause/terminal state. One atomic snapshot for core and evidence, not separate files with an unsafe commit gap. An unavailable or inconsistent ledger halts; restart never resets count. Existing core state serialization and validation should be reused or wrapped; no modification of legacy source required for the initial proof. M03 mock harness must not invoke desktop, live GitHub, tunnel or original service. Use synthetic-only data and temp directory, no real credentials.
